## 0. 30 秒电梯演讲（背这一版）

> 我做了一个**个人收藏夹 RAG 系统**：把小红书收藏过的笔记（图文 + 视频）抓下来，图片走 OCR、视频走抽帧 OCR + 语音转写，统一变成可检索的文本索引，然后做混合检索 + 重排 + 带引用的问答。
> 核心不在"接了个 RAG"，而在**工程闭环**：采集有断点续传和风控策略，多模态内容统一进同一套索引，检索链路全本地模型（数据不出本机），并且自己写了三套离线评测来量化召回和生成质量——26 条标注集上 Recall@5 0.91（生产配置）/ 0.965（候选池放大后）。后来又补了 Agent 决策层和长期记忆层。

**2 分钟版本**（讲完 30 秒版后展开，按 "为什么 → 怎么做 → 结果" 三段）：

1. **为什么**：我自己收藏了几百篇菜谱/育儿笔记，用的时候找不到。通用搜索搜不到收藏内容，小红书自己的搜索又只能按关键词。
2. **怎么做**：五层——采集（Playwright 持久化登录态）→ 多模态处理（OCR/ASR）→ 索引（bge-m3 + BM25 + LanceDB）→ 检索（RRF 融合 + rerank 重排 + CRAG 自修正）→ 生成（带 `[n]` 引用可跳原帖）。上层有 Agent 决策循环（LangGraph）和长期记忆（对话摘要 + 用户画像双轨）。
3. **结果**：91 篇笔记 / 574 张图 OCR / 21 个视频转写 / 297 个 chunk，检索 Recall@5 0.91、MRR 0.94，单条查询 0.83 秒；生成端 RAGAS 自测 faithfulness 0.70。

## 3. 核心实现要点（面试深挖，每个都能讲 3 分钟）

### 3.1 检索链路（最值得讲）
- **混合检索**：向量（语义）+ BM25（精确关键词）RRF 融合。为什么必要：配方用量常写在图片里，OCR 出来的 chunk 开头是噪声，向量检索打分低会被挤掉，但关键词命中能捞回来。最新实测（池 20）：Recall@5 0.951 → **0.965（+1.4pp）**；BM25 的真实价值更多在**鲁棒性**——"2勺生抽""山药栗子"这类精确数字与专有名词，向量容易糊、BM25 稳定命中，且它给系统提供了一条**不依赖模型的兜底召回路径**。
- **候选池是命门**：`rerank.top_k_in` 从 6 调到 20，Recall@5 **0.910 → 0.965（+5.5pp）**；但候选越多 rerank 越慢（CPU 每对 ~1.2s，2.26s/query），所以必须可配置、并在服务启动时预热。生产当前选池 6 是延迟优先的取舍。
- **同笔记补全**：配方类笔记的用量在图 OCR chunk 里，rerank 只用前 160 字符打分会被淘汰 —— 只要某笔记有一个 chunk 进 topN，就把它在候选里的其他 chunk 补进结果尾部（每笔记最多 3 条）。
- **CRAG-lite 自修正**：top1 rerank 分 < 0.75 → LLM 改写检索词重检一次，更好才采纳；仍低则结果标 `low_confidence`，生成端如实回答"收藏里没有提到"，**不编造**。

### 3.2 踩过的硬坑（面试官最爱听）
1. **reranker 分数语义差异**：本地 `FlagReranker.compute_score` 默认返回原始 logits（正例 3.9 / 负例 0.56），与官方 API 的 sigmoid 两极化行为不同，CRAG 阈值 0.05 完全失效。修法：`normalize=True` + 用 26 条评测集重新标定阈值到 **0.75**（正例全部 >0.97，负例最高 0.64）。**教训：同一模型不同部署形态，分数语义不同，阈值必须实测。**
2. **弱模型 function calling 退化**：glm-4-flash 在 4 个工具 + 长 prompt 时，偶发把工具调用写成纯文本 `search("词",1)`。修法：正则按位置参数表还原成结构化 `tool_call`（覆盖括号式与引号式两种退化形态）。**教训：function calling 的可靠性是模型能力问题，不是协议问题，Agent 框架必须有文本兜底。**
3. **LLM 结构化输出不稳**：同一模型输出 JSON 时会出现伪 JSON（`["k":"v"]`）、照抄提示词里转义后的 `{{`、末尾多 `]}`。画像抽取因此从 JSON 改为**按行文本解析**，稳定性提升一个数量级。
4. **MCP stdio 协议污染**：MCP 要求 stdout 只承载 JSON-RPC，而 loguru 默认打 stdout（带 ANSI 颜色）—— 一行日志混入就让客户端解析失败。修法：启动前把日志全部改道 stderr。
5. **Windows 线程加载模型死锁**：MCP 工具在 anyio worker 线程执行，在线程内首次 import torch / 加载 bge-m3 会死等挂起（0 CPU、内存停 150MB）。修法：预热必须在 `mcp.run()` 之前的主线程做。
6. **OCR 噪声污染索引**：视频帧 OCR 的 `<|LOC_n|>` 定位标记混进 chunk，重建索引后 LOC 标记 62→0，chunks 234→218，检索耗时 35-75s → 9-14s。

### 3.3 工程化（体现"能落地"而不只是 demo）
- **断点续传**：每阶段状态落库，任何一步失败停在原状态，重跑自动跳过已完成项（`ocr_done`、`asr_status`、索引 `note_id` 判定）。
- **风控策略**：随机限速（列表 1.2-1.8s、详情 1.5-3.0s）、批量暂停、验证码 10min / 461 错误 30min 冷却、每日全量同步上限 2 次。
- **优雅降级**：LLM 未配 key / 接口失败 → 只出检索结果 + 一条提示，不报错；BM25 失败 → 退回纯向量；rerank 失败 → 退回向量原序；**任何一环挂掉系统仍可用**。
- **成本控制**：LLM 用免费 glm-4-flash；embedding/rerank/OCR/ASR 全部本地优先，仅极少数难样本上云（OCR 574 张里只有 18 张走云 API）。

## 4. 量化指标（实测，2026-09-11）

### 4.1 数据规模（当前库）

| 指标 | 数值 |
|---|---|
| 笔记总数 | **91**（图文 70 / 视频 21） |
| 图片 OCR 完成 | **574 / 574**（本地 RapidOCR 411、云端 VLM 兜底 18、无文字 145） |
| 视频 ASR 完成 | **21 / 21**（转写文本共 **15,862** 字，全部本地 SenseVoiceSmall） |
| 索引 chunk 数 | **297** |
| 检索耗时（生产配置池 6，含 rerank） | **0.71s / query** |
| 检索耗时（候选池 20） | 2.26s / query（效果更好，见 4.2） |

### 4.2 检索质量（26 条人工标注评测集）

评测集 26 条（24 正例 + 2 负例，人工依据笔记原文标注），**2026-09-11 在 297 chunk 语料上重跑**：

**① 生产配置（候选池 = 6，即线上 `rerank.top_k_in` 实际值）**

| 模式 | Recall@5 | MRR@10 | nDCG@5 | 检索耗时/query |
|---|---|---|---|---|
| 纯向量 dense | 0.910 | 0.958 | 0.912 | 0.12s |
| +BM25 hybrid | 0.910 | 0.938 | 0.910 | 0.03s |
| **+rerank（生产实际链路）** | **0.910** | **0.917** | **0.886** | **0.71s** |

**② 候选池扩大到 20（对照实验）**

| 模式 | Recall@5 | MRR@10 | nDCG@5 | 检索耗时/query |
|---|---|---|---|---|
| 纯向量 dense | 0.951 | 0.967 | 0.928 | 0.12s |
| +BM25 hybrid | **0.965** | **0.958** | **0.946** | 0.03s |
| +rerank | 0.965 | 0.938 | 0.925 | 2.26s |

**结论（两个都能讲，别只讲好的那个）：**

1. **候选池是最大的效果杠杆**：6 → 20 让 Recall@5 从 0.910 → **0.965（+5.5pp）**，代价是耗时 0.71s → 2.26s（CPU rerank 每对 ~1.2s）。生产当前选池 6 是**延迟优先的取舍**，不是效果最优解。
2. **rerank 在我这个规模下是负增益（诚实披露）**：池 6 时 MRR 0.938→0.917、nDCG 0.910→0.886；池 20 时 MRR 0.958→0.938、nDCG 0.946→0.925；Recall 完全不变（rerank 只重排、不改召回集合）。原因分析三条：
   - rerank 打分只取 chunk **前 160 字符**，而配方/用量的关键信息常在 OCR chunk 尾部，等于让 reranker 看着标题打分；
   - 用的是 `bge-reranker-**base**`（非 v2-m3），中文短文本区分度弱于 bge-m3 本身的向量召回；
   - 语料仅 297 chunk、干扰项少，dense 已经很强，重排的纠错空间小。
   改进路径已明确（换 v2-m3 / 打分长度放宽到 400 字符 / 只在候选池 ≥20 时启用 rerank），**这是下一步的优化项而不是已完成项**。

> 面试话术：这题我不会藏数字。"我实测发现 rerank 在我这个规模上是负收益，所以我没有把它当成亮点吹，而是定位到原因是打分截断太短 + base 版模型能力有限 —— 这比'我加了 rerank 效果变好了'更能说明我真的跑了对照实验。"

## 5. 简历条目（可直接复制）

### 5.1 项目标题（选一个）

- **「xhs-rag」个人知识库 RAG 系统** | 独立开发 | Python · LangGraph · LanceDB · Docker | 2026
- 小红书收藏夹多模态 RAG 问答系统（独立项目，MIT 开源）

### 5.2 项目描述（一段式）

> 面向个人收藏内容的**端到端 RAG 系统**：采集（Playwright 持久化登录 + 反自动化）→ 多模态处理（图片 OCR / 视频抽帧 + 语音转写）→ 混合检索（bge-m3 向量 + BM25 + RRF + rerank 重排）→ 带引用生成的流式问答，并叠加 Agent 决策层与长期记忆。检索链路全本地模型，数据不出本机。已处理 91 篇笔记 / 574 张图 / 21 个视频共 297 个 chunk，自建 26 条标注评测集，检索 Recall@5 达 0.965（生产配置 0.910），单查询 0.71s。

### 5.3 职责与成果（bullet 版，挑 4-5 条用）

- 设计并实现**多模态统一索引管线**：图片 OCR（本地 RapidOCR + 云端 VLM 兜底）与视频抽帧 OCR + ASR 转写（本地 SenseVoiceSmall）产物统一切分为 297 个 chunk 进入同一向量索引，使**视频语音内容可被语义检索**命中。
- 构建**混合检索 + 重排链路**（bge-m3 1024 维 + jieba BM25 + RRF 融合 + bge-reranker 重排），通过对照实验定位到**候选池是最大杠杆**（6→20 使 Recall@5 从 0.910 升至 **0.965，+5.5pp**），生产按延迟优先保留池 6（0.71s/query）。
- 自建 **26 条人工标注评测集**并跑三模式对照，诚实定位到 rerank 在本规模下为负增益（打分截断 160 字符 + base 版模型能力所限），据此提出改进路径而非粉饰指标。
- 实现 **CRAG-lite 检索自修正**：以 rerank 归一化分数实测标定阈值 0.75 触发查询改写重检，低置信结果如实回"库里没有"而非编造，**显著降低幻觉**。
- 搭建**三套离线评测**（检索 Recall/MRR/nDCG、LLM-as-judge 三维、RAGAS 四指标自实现，零重依赖），评测脚本复用生产组件，形成可回归的质量护栏。
- 实现 **Agentic RAG 决策层**（LangGraph StateGraph + 原生 function calling，4 个只读工具 + 伪调用自愈 + 重试分层），多跳问题自动拆解检索，行为测试 5/5 通过。
- 设计 **M11 长期记忆双轨**（对话摘要 + 用户画像）：在线零成本落对话流水、离线 LLM digest 加工、生成前注入背景注记并显式声明"非事实来源"以防幻觉。

## 6. 面试高频问答（含追问预案）

**Q：为什么不用 LangChain / LlamaIndex，而是自己写？**
> 检索链路只有 300 行核心逻辑，框架的抽象层反而让我没法精确控制候选池和融合策略——而这两个恰恰是效果差异最大的地方（候选池 6→20 就带来 7.6pp）。Agent 层我用了 LangGraph，因为那里确实需要显式状态机和可审计路由。**框架为需求服务，不是为简历服务。**

**Q：混合检索为什么必要？只用向量不行吗？**
> 不行。我的场景里配方用量、时间这些关键信息常写在图片里，OCR 出来的 chunk 开头是噪声，向量打分很低会被挤掉；但用户问"2勺生抽"这种精确关键词，BM25 能直接命中。实测 hybrid 比纯向量 +3.5pp。而且两路分数不可比，所以用 RRF 按排名融合而不是加权求和。

**Q：你加了 rerank，效果提升了多少？**
> （诚实）**没有提升，反而略降** —— 池 6 时 MRR 0.938→0.917，池 20 时 0.958→0.938，Recall 完全不变（rerank 只重排不改召回集合）。我定位到三个原因：① 打分只取 chunk 前 160 字符，而配方用量常在 OCR chunk 尾部，等于让 reranker 看标题打分；② 用的是 bge-reranker-base 而非 v2-m3，中文短文本区分度不够；③ 297 chunk 的小语料里 dense 本身已经很强，重排纠错空间小。
> 改进路径已明确：换 v2-m3、打分长度放宽到 400、只在候选池 ≥20 时启用。**我选择如实披露并给出归因，而不是把 rerank 包装成亮点** —— 对照组跑出来是负收益，本身就是结论。

**Q：rerank 阈值 0.75 怎么来的？**
> 实测标定的。踩过坑：本地 FlagReranker 默认返回原始 logits（正例 3.9 / 负例 0.56），跟官方 API 的 sigmoid 两极化行为完全不同，一开始沿用 0.05 的阈值完全失效。改成 `normalize=True` 后，在 26 条评测集上测出正例 top1 全部 >0.97、负例最高 0.64，0.75 正好落在分离边界。**结论：同一模型不同部署形态，分数语义不同，阈值必须实测，不能抄。**

**Q：幻觉怎么控制？**
> 四层：① system prompt 硬约束"只依据片段、数字必须原样保留、片段没提到就说没有"；② 每条事实句末强制 `[n]` 引用，前端可点击跳原帖核验；③ CRAG-lite 低置信如实告知不编造；④ 长期记忆注入时显式声明"这是背景不是检索片段，禁止当作新事实引用"。

**Q：为什么坚持本地模型？成本/延迟怎么权衡？**
> 这是个人数据库，收藏内容包含个人生活信息，本地优先是设计前提；而且 embedding/rerank 全本地让单次查询成本为 0。延迟用三个手段压：OCR 噪声清洗减少无效 chunk、候选池可配置、query 编码 + 检索结果双层缓存（重复提问秒回）。实测 35-75s → 9-14s。

**Q：Agent 层为什么选 LangGraph？**
> v1 是手写 while 循环，能跑但失败重试和步数上限都藏在循环里，不可审计。迁到 StateGraph 后，`llm→(条件路由)→tools→llm/finalize→END` 画在图上，max_steps 从循环计数升级成**路由条件**，LLM 与工具各有独立重试策略。只用了编排能力，LLM 调仍是 requests 直发 function calling，checkpointer 留了扩展位但没启用——个人库没有中断恢复场景，不为了用而用。

**Q：数据只有 297 个 chunk，指标可信吗？**
> （诚实回答）统计意义有限，我不拿它代表大库表现。评测的价值在**同口径回归对比**——我用它来判断"改动是变好还是变差"，不是横向跟别的系统比绝对值。扩展到十万级我预期要重新引入 ANN 索引 + 扩大候选池，这部分设计已经想好但没做。

**Q：多模态内容怎么进检索的？**
> 统一降维到文本：图片 → OCR 文本，视频 → 抽关键帧 OCR + 语音转写文本，都切成 chunk 进同一张向量表，所以**用户问"冬瓜蒸肉饼怎么做"，能命中视频里的语音转写**（实测相似度 0.9993）。代价是丢失了视觉语义，这点我在局限里会主动讲。

**Q：MCP 接入踩了什么坑？**
> 三个：① stdout 只能走 JSON-RPC，日志必须改道 stderr；② 任何模型加载必须在主线程预热，worker 线程里加载会死锁；③ `mcp` 2.x 把 FastMCP 改名 MCPServer，版本要钉 `<2`。

## 7. 诚实：局限与下一步（主动讲，加分）

0. **rerank 未达预期**（实测负增益，见 4.2）：打分截断 160 字符 + base 版模型能力所限，改进路径已明确但未实施。
1. **语料规模小**（297 chunk）：小表走 flat 精确扫描是对的，但 ANN 路径未经验证；扩到十万级要重做索引策略。
2. **多模态只做了"降维到文本"**：图片/视频的视觉语义没有向量化，做不到"以图搜图"。
3. **查询入口只有文本**：不能拍图问、不能语音问（OCR/ASR 是采集侧管线，不是查询侧）。
4. **Agent 是单 Agent 线性编排**：无并行工具调用、无 plan-and-execute。
5. **LLM-as-judge 有自评偏差**：裁判与被评同款模型，分数只用于回归趋势，不用于跨系统横评（实测同 query 三轮 1.00→0.86→0.76 抖动）。
6. **未做微调**：当前规模下检索 + prompt 已够用，没有需要参数化记忆的场景；若做，微调数据必须与 RAG 知识库严格隔离（用公开语料训练、用收藏库评测）。
